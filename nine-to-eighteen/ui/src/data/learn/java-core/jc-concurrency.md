## Введение

Два потока без договорённости о памяти видят разное. volatile делает запись видимой, но не делает составное действие атомарным. synchronized и пул закрывают другие дыры.

## Раздел: Границы

`i++` даже у volatile не атомарен: прочитали, прибавили, записали. Для счётчика нужен атомарный тип или блок. Пул потоков ограничивает число, очередь задач и переиспользование. `new Thread` на каждый запрос так не умеет. Общую HashMap без синхронизации два потока портят.

## Раздел: Ответ вслух

volatile я беру, когда нужна видимость одного флага. Счётчик так не защищаю. Критическую секцию закрываю синхронизацией или готовым атомарным классом. Потоки беру из пула, чтобы не создавать их без предела.

## Раздел: Плохой ответ

Плохой ответ: «поставил volatile на счётчик, гонок нет». Прибавление всё ещё из трёх шагов.

## Раздел: Термины

Видимость — visibility. Гонка — race. Атомарность — atomicity. Пул — thread pool. Критическая секция — critical section.

## Тест

### volatile на int и i++. Гонка возможна?

**Ответ:** да

**Пояснение:** Нет атомарности прибавления.

### Два потока пишут в HashMap без замка. Можно?

**Ответ:** нет

**Пояснение:** Структура рвётся.

### Зачем пул, если можно new Thread?

**Ответ:** предел и переиспользование

**Пояснение:** Иначе потоков станет сколько запросов.

### Флаг остановки volatile. Уместный случай?

**Ответ:** да, если это одна запись

**Пояснение:** Видимости хватает.

### synchronized на весь метод длинного отчёта. Чем плохо?

**Ответ:** держат замок зря

**Пояснение:** Секция должна быть короткой.

## Anki

Back: Видимость записи другим потокам.

### Front: Что volatile не даёт?

Back: Атомарность составного действия.

### Front: Почему i++ не атомарен?

Back: Чтение, прибавление и запись — разные шаги.

### Front: Зачем thread pool?

Back: Ограничить число потоков и переиспользовать их.

### Front: Общая HashMap без синхронизации?

Back: Нельзя, если пишут несколько потоков.

### Front: Что такое race?

Back: Итог зависит от порядка без договорённости.
